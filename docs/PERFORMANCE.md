# mica: измерение ресурсов

## Условия

Проверка 7 ноября 2026 года, MacBook Air MacBookAir10,1, Apple M1 с 8 ядрами, 8 ГБ RAM, macOS 15.7.5 build 24G624, Xcode 26.1. Приложение собирается для arm64 с deployment target 15.4, release optimization. Фоновый рабочий стол не очищался от приложений пользователя, поэтому это воспроизводимая методика и результаты конкретного прогона, а не лабораторное сравнение браузеров.

Встроенная блокировка включена, расширения в измерительном сценарии не загружаются. Открывается отдельный QA-профиль. Нет авторазгрузки; все созданные и посещённые вкладки имеют настоящий WKWebView. Пустое окно содержит только нативную начальную страницу. Для одной вкладки используется Wikipedia, для десяти — опубликованный список ниже. Медиа автоматически не воспроизводятся, пользовательские аккаунты не используются.

| Номер | URL |
|---|---|
| 1 | https://www.wikipedia.org |
| 2 | https://github.com/WebKit/WebKit |
| 3 | https://webkit.org/blog/ |
| 4 | https://developer.apple.com/documentation/webkit |
| 5 | https://www.swift.org/documentation/ |
| 6 | https://www.w3.org/TR/websockets/ |
| 7 | https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API |
| 8 | https://www.youtube.com/watch?v=aqz-KE-bpKQ |
| 9 | https://www.openstreetmap.org |
| 10 | https://www.bbc.com/news |

Окно повторного прогона фиксировано: content size 1180 на 780 pt, contentLayoutRect 1180 на 752 pt. Каждый конечный URL перенаправления записывается отдельно. Каждая страница получает до 35 секунд для завершения первоначальной загрузки. Фактические заголовки, ошибки, успешность и время каждого URL сохраняются в `pages.json`. Наличие WKWebView и успешная загрузка — разные поля. Если URL недоступен, его нельзя засчитывать как успешно загруженную репрезентативную страницу. Результаты сети и сайты могут измениться при повторении.

## Команды

```sh
cd macos
scripts/build.sh release
python3 scripts/benchmark.py
# Короткий повтор без длительной сессии:
python3 scripts/benchmark.py --quick
```

Для скриптов измерений нужен Python 3. Среда исполнения самого приложения Python не требует. Скрипт последовательно запускает 0, 1 и 10 вкладок, собирает снимки и фоновый CPU. Десять вкладок остаются открытыми 15 минут; дополнительные снимки делаются примерно через 300, 600 и 850 секунд от старта процесса. Приложение завершает только собственный тестовый процесс по окончании заданного интервала. Не следует открывать другие приложения на системном WebKit в этот интервал, если используется определение PID по разнице с baseline.

Результаты — `work/benchmark-YYYYMMDD-HHMMSS/`. В каждом сценарии: baseline процессов, момент готовности окна, список страниц, групповая память, swap, VM statistics, давление памяти и CPU. Снимок вручную:

```sh
cd macos
python3 scripts/measure.py baseline --out work/before
python3 scripts/measure.py snapshot --pid PID --baseline work/before/baseline.json --out work/snapshot
python3 scripts/measure.py cpu --pid PID --baseline work/before/baseline.json --out work/cpu --seconds 60
```

При неоднозначности передайте известные WebKit PID в `--webkit-pids PID1,PID2`. Обязательно прочитайте `attribution.json`. WebKit XPC часто имеет PPID=1; его нельзя искать только среди дочерних процессов приложения. Скрипт выбирает новые системные WebKit PID относительно baseline, исключая процессы другого браузера. Это способ отбора кандидатов, а не доказательство ownership. Повторное использование существующего XPC может дать недоучёт; запуск другого WebKit-клиента — переучёт. В этой проверке список кандидатов сверялся с запуском и завершением тестового приложения.

## Память и CPU

`footprint` запускается сразу с приложением, WebContent, GPU и Networking. В итог берётся его групповое `total footprint`, с учётом общей памяти средствами самого инструмента. RSS не суммируется и не выдаётся за физическую память. Файл содержит также compressed/swapped категории, ошибки и per-process значения. Для глобального контекста сохраняются `sysctl vm.swapusage`, `vm_stat` и `memory_pressure -Q`. Swap относится ко всей системе, не только к mica.

Фоновый CPU определяется по разнице накопленного CPU time процессов за 60 секунд; поле `groupCpuPercent` — доля одного ядра, суммарно по фиксированному набору PID. PID, появившиеся или завершившиеся внутри интервала, не учитываются в этой оценке; исходные двухсекундные отсчёты сохранены. Окно сворачивается, web views остаются живыми. Нельзя сравнивать этот тест с foreground-анимацией, воспроизведением видео или выгруженными вкладками.

Время старта измеряет внешний процесс от `Popen` до появления ready-marker после создания первого окна, с точностью опроса 50 мс. Это тёплый запуск без перезагрузки ОС, а не чистый холодный старт. Для проверки отрисовки и интерактивности отдельно используется настоящий UI. Измерение переключения в `pages.json` фиксирует dispatch модели и один executor yield; оно не называется задержкой от ввода до пикселя.

## Профилирование и изменения

1. Убрана повторная компиляция одинакового списка правил при каждом запуске: отпечаток JSON проверяется перед чтением скомпилированного списка из локального WKContentRuleListStore. Разные профили имеют разные stores.
2. Измерительный запуск больше не загружает расширения перед их выключением. Предварительный прогон выявил, что такой порядок оставлял WebKit cache-процессы даже у пустого окна. Предварительный прогон отделён от окончательного и не подмешивается в таблицу результатов.
3. Изменение плотности фона не переназначает NSApp.appearance и не пересохраняет сессию. Запись настроек объединяется задержкой 150 мс после изменений, без постоянного таймера.
4. Проверка ZIP и потоковый SHA-256 вынесены из main actor; размер вывода архивного инструмента и время выполнения ограничены.
5. В debug-прогоне `leaks` обнаружил 0 утечек; отдельная проверка подтвердила освобождение WKWebView после закрытия вкладки. Это не доказательство отсутствия всех возможных утечек. Неподписанный для отладки предварительный запуск инструмента был ограничен системой и не считается равноценным финальному debug-прогону.

Точные результаты конкретных прогонов сохраняются рядом с этим документом в `RESULTS.json` и таблице `docs/VALIDATION.md` после завершения измерений. Отсутствующая строка не является нулём.

## Пределы

Сопоставимый прогон других браузеров не выполнен: существующая рабочая сессия и другая сборка WebKit не подходят для сравнения при фиксированных вкладках и одинаковой блокировке. Измерения mica не доказывают превосходство над другими браузерами. Для честного сравнения нужен отдельный контролируемый профиль, одинаковые URL, состояние кешей, блокировка, видимость и подтверждение живых вкладок.

15 минут — ограниченный soak test. Многочасовая работа, рабочие аккаунты, конференция WebRTC с удалённым участником, активное потоковое видео и поведение при искусственном сильном memory pressure не проверялись. Никакого искусственного давления на рабочую машину пользователя не создавалось. Эти ограничения нельзя заменять расчётными цифрами.

## Измеренные результаты

Длительный прогон `benchmark-20261107-221446`: 10 живых WKWebView, начальный footprint группы 1256.8 МиБ, снимки на 300/600/850 секундах — 986.7 / 967.8 / 1005.6 МиБ. Первый фоновый минутный интервал — 10.14% одного ядра, поздний — 8.02%. Две загрузки отмечены `loaded=false` из-за проверки исходного host: они перенаправили на docs.swift.org и websockets.spec.whatwg.org и имели реальные заголовки. Это ошибка измерительного условия, она явно оставлена в исходном отчёте.

После исправления учёта перенаправлений и задания фиксированного окна выполнен отдельный короткий повтор `benchmark-20261107-224404`. В нём подтверждены 10 из 10 загрузок и 10 живых WKWebView. Политика autoplay требует пользовательского действия. Различия условий и кешей не позволяют приписать изменение цифр одной оптимизации.

| Сценарий повторного прогона | Групповой footprint | Готовность первого окна, тёплый запуск | Фоновый CPU, около 60 с |
|---|---:|---:|---:|
| Пустое окно, 0 WKWebView | 22.1 МиБ | 0.495 с | Не измерялся |
| 1 страница | 162.6 МиБ | 0.275 с | 0.24% одного ядра |
| 10 страниц, 10 живых WKWebView | 1506.6 МиБ | 0.267 с | 4.61% одного ядра |

Это значения с конкретных снимков, не верхние границы RAM. Время готовности окна не включает ожидание загрузки всех сайтов. Медиана dispatch/yield переключения для долгого прогона около 24.7 мс; это не input-to-photon latency. JSON содержит фактические значения каждого прохода, глобальный swap и исходы страниц. В окончательную упаковку дополнительно включено освобождение security-scoped доступа при очистке загрузок; измерительные сценарии загрузок файлов не выполняют.

## Windows

`mica.exe --qa --benchmark=N` (N = 0, 1 или 10) открывает N вкладок, ждёт 20 секунд и пишет `benchmark-N.tsv` в `%LOCALAPPDATA%\mica\QA`: private bytes самой mica и каждого процесса WebView2 с его ролью (браузер, рендерер, GPU, утилиты) из `GetProcessExtendedInfosAsync`. Это private working set, а не footprint macOS, поэтому числа двух платформ напрямую не сравниваются. Измерений на Windows ещё нет.
